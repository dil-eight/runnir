# Core Process Implementation Plan

Status: proposed, 2026-10-17. Decision: [ADR 0004](../decisions/0004-single-core-process-grpc.md). Each phase ships independently, keeps existing Swift sources and `core.v1.version` working, and is verified with the commands in AGENTS.md.

## Starting Point

- Core: `core/cmd/runnir` (`version`, `rpc`) and `core/internal/ipc` (one-shot JSON-RPC). No repository, workflow or event code.
- Swift: `IPC/StdioCoreTransport.swift` and `CoreClient.swift` (one child per request). `DesktopCoordinator` owns windows, registry and sessions; `Repository`/`Workflow` models exist in `Core/Models`.
- Contracts: `contracts/ipc/v1/version.schema.json` only.

## Phases

| # | Outcome | Main work | Done when |
| --- | --- | --- | --- |
| 0 | Decisions settled | Review ADR 0004; pick gRPC-Swift version, Go YAML library; confirm UDS works in the sandbox with a spike | Open decisions in the ADR are closed or recorded |
| 1 | Contract | `contracts/grpc/runnir/core/v1/runnir_core.proto`, generated Go and Swift committed, README on regeneration | `go build ./...` and Xcode build pass with generated code |
| 2 | Core server | `core/internal/server` gRPC over UDS, `HealthCheck`, lock file, parent-death exit, graceful shutdown; `runnir-core serve` command | Second start refuses; killing parent ends Core; `go test -race ./...` |
| 3 | Repository Manager | `core/internal/repository`: contexts keyed by `repository_id`, idempotent Open, Close, Refresh, per-context locking | Reopening yields one context; refresh of A does not block B (race tests) |
| 4 | Workflows | Read `.github/workflows`, resolve branch, parse YAML into a graph; bounded file sizes; no execution | Fixtures: no files, malformed, oversize, worktree `.git` file, both extensions |
| 5 | Events | `SubscribeEvents` with bounded per-subscriber buffers, repository-scoped events | Slow subscriber cannot grow memory; ordering per repository tested |

| 7 | Swift lifecycle | `CoreProcessSupervisor` (launch, health wait, reconnect, restart prompt), gRPC client behind a protocol next to `CoreClient` | Exactly one process across several windows; quit ends Core; crash then reconnect |
| 8 | Swift integration | Map `DesktopCoordinator` repository open/close/refresh to RPCs; per-window event filtering; keep local fallbacks until parity | Two to three windows show different repositories; closing one leaves others intact |
| 9 | Diagnostics | Memory and CPU sampling script at 1, 3, 10 repositories; results recorded in a verification doc | Numbers documented against the 300 MB target, honestly |
| 10 | Docs and MCP readiness | Update IPC, overview, lifecycle and MCP docs; confirm no API change is needed for an MCP adapter | Docs match shipped behavior only |

## Verification

Core: `go test ./...`, `go vet ./...`, `go build ./...` from `core/`, plus `-race`. App: the build and `-only-testing:RunnirTests` commands from AGENTS.md. Acceptance criteria 1 to 10 from the proposal map to phases 2 to 9; a process-count check (one `runnir-core` with ten repositories open) is automated in phase 8.

## Risks

- UDS under the App Sandbox works in the spike (grpc-swift 2), but that client needs macOS 15; the project deployment target was raised from macOS 14.0 to 15.0 for it.
- New dependencies conflict with the stdlib-first rule and add binary size.
- Stale socket or lock after a crash can block restart; the lock file must use an OS advisory lock, not mere existence.
- Dual paths (stdio and gRPC) can drift; keep the stdio path limited to version until retired.

## Phase 0 Spike Results (2026-10-17)

Setup: ad-hoc signed `.app` with `app-sandbox` + `network.client` only (same as `Runnir.entitlements`), a pure Go helper (`CGO_ENABLED=0`, grpc-go 1.84.0, standard health service, about 14.7 MB) signed with `app-sandbox` + `inherit` (as `macos-helper.entitlements`), and a Swift client on grpc-swift-2 2.4.4 + grpc-swift-nio-transport 2.11.0. Run on macOS 27.0.1, Swift 6.4, with the code in a scratch directory outside the repository.

- The sandboxed app launched the inherited helper with `Process`; the helper bound a Unix socket in the app container (`~/Library/Containers/<bundle id>/Data/Library/Caches`); the client connected and `grpc.health.v1.Health/Check` returned SERVING. No `network.server` entitlement was needed.
- Not run outside an app launch: a sandboxed binary started from a shell traps (exit 133) because it has no container.
- **Deployment target:** grpc-swift 2 requires macOS 15; the Xcode project targeted macOS 14.0, so the target was raised to 15.0 (decision 2026-10-17). grpc-swift 1.x was not evaluated.
- **Socket path length:** `sun_path` holds 103 bytes. The container path is already about 83 characters with a short bundle id, so the socket name must be short and the length checked at startup; fall back to a shorter directory if needed.
- Stale socket after an unclean exit was left in place; the server must remove it only under the lock (plan phase 2).
- Not verified: a Developer ID signed and notarized build, a real Xcode-built app, grpc-swift 1.x, the Swift gRPC dependency's effect on app size and CI time, helper behavior when the parent dies.

## Progress

- Phase 0: done, see spike results above.
- Phase 1: done. Contract and generated code committed; deployment target raised to macOS 15.0.
- Phase 2: done in Core, not yet launched by the app. `runnir serve --socket PATH [--exit-on-stdin-eof]` serves `HealthCheck` over a Unix socket (mode 0600) under an advisory `flock` on `PATH.lock`. A second instance exits with code 3 without touching the running socket; a stale socket is removed only under the lock; SIGINT/SIGTERM or stdin EOF stops it gracefully and removes the socket. Paths over 103 bytes are rejected. Verified with Go tests (`-race`), cross-builds for darwin/linux/windows, and a manual `grpcurl` call. The other RPCs return `Unimplemented`. `resident_memory_bytes` is currently Go's `MemStats.Sys`, not true RSS (phase 9). The lock file stays on disk after exit, which is harmless. Parent-death behavior has only been tested with a closed pipe, not an app crash.
- Phase 3: done in Core. `internal/repository.Manager` keeps one context per repository; a registry lock guards only the map, and each context serializes its own scans. `OpenRepository` resolves symlinks and treats the same directory (same path or `os.SameFile`) as the same repository, so concurrent and repeated opens share one context and one initial scan; the id is `repo_` plus a hash of the first resolved path and stays stable across close and reopen. `CloseRepository` cancels a running refresh, which then returns not found; a failed initial scan registers nothing. Open, Refresh and Close are exposed over gRPC with `InvalidArgument` and `NotFound` mapping, and `HealthCheck` reports the open count. Race tests (`go test -race`, repeated) cover idempotent concurrent open, ten independent repositories, refresh isolation, close during refresh, serialized refreshes, failed-open sharing and an open/close/refresh mix. Scanning is still a no-op (branch empty, zero workflows) until phase 4. The `repository_id` mapping to the Swift workspaceId (ADR 0004 open decision) is unresolved: the Swift side must use the Core-issued id or keep its own mapping. Events are produced through a callback and not yet streamed (phase 5).
- Phase 4: done in Core. `internal/scanner` reads the branch from `.git/HEAD` (also linked worktrees through a `.git` file; detached HEAD or a non-local ref gives an empty branch) and parses `.github/workflows/*.yml|yaml` into name, triggers and the job graph (`name`, `needs`) in file order. Expressions are kept verbatim and nothing is evaluated. Limits: 1 MiB per file, 200 files, 1000 jobs per workflow. Symlinked `.github`, `workflows`, files and nested directories are not followed, so a scan cannot leave the repository root. A bad file yields a per-workflow `parse_error` and does not fail the scan. YAML aliases are never expanded, so alias bombs cost nothing. `ListWorkflows` serves the last snapshot; external edits appear only after `RefreshRepository`. Verified by scanner and gRPC tests (`-race`) and by opening this repository through `grpcurl` (branch and 3 workflows found). Dependency added: `go.yaml.in/yaml/v3` 3.0.5 (the maintained fork of yaml.v3; MIT and Apache-2.0; pure Go).
- Go toolchain raised to 1.27.2 (`core/go.mod`; CI follows it through `go-version-file`) and dependencies updated (x/net 0.61.0, protobuf 1.36.12). `govulncheck` reported called vulnerabilities in `net/http`, `crypto/tls` and `x/net` on Go 1.25.7; after the upgrade it reports none. README and CONTRIBUTING now say Go 1.27+. Older notes in `foundation-verification.md` describe Go 1.25.7 runs and stay as historical records.
- Phase 5: done in Core. `internal/events.Bus` gives each subscriber a fixed queue (default 256). `Publish` never blocks; a subscriber whose queue is full is closed and the stream ends with `RESOURCE_EXHAUSTED`, so memory stays bounded and the client resubscribes and reloads state. Sequences are assigned under one lock, so delivery order matches the sequence and gaps are detectable. `SubscribeEvents` sends `CORE_READY` first with the baseline sequence, then repository events (`REPOSITORY_OPENED`, `REPOSITORY_REFRESHED`, `REPOSITORY_CLOSED`) filtered by `repository_ids`; events without a repository always pass. On shutdown the bus closes first, so open streams end with `UNAVAILABLE` and the graceful stop is not held up. Tested with `-race`: ordering, filtering, overflow isolation, publish never blocking, shutdown with an open stream, and a stalled-client handler test. Limitation: a client that stops reading keeps one handler goroutine blocked in `Send` until its connection closes; its queue stays bounded. `WORKFLOW_*` events arrive with phase 6.
- Phase 6: done in Core. `internal/execution.Coordinator` runs at most 3 executions at once (configurable) and queues the rest in a bounded FIFO (100); a full queue returns `RESOURCE_EXHAUSTED`. Each execution gets a deep copy of the workflow taken at start, so a later refresh or file edit does not affect it. Events: `WORKFLOW_STATUS_CHANGED` (queued, cancelled), `WORKFLOW_STARTED`, `WORKFLOW_COMPLETED`, `WORKFLOW_FAILED`, published under the coordinator lock so one execution's events stay in order. `StartWorkflow` rejects unknown repositories and workflows (`NOT_FOUND`) and workflows with a parse error (`FAILED_PRECONDITION`). Closing a repository cancels its executions; shutdown cancels all and waits for runners. A cancelled running execution keeps its slot until its runner returns. The runner is a stub that fails every job with "workflow execution engine is not available in this build", so no run is reported as successful. There is no cancel RPC in contract v1; cancellation is internal (repository close, shutdown). Tests with `-race` (the FIFO test was repeated 100 times) cover the limit under concurrent starts, FIFO dispatch, cancel of queued and running executions, per-repository cancel, queue bound, snapshot isolation, shutdown, and the gRPC path including cancel on repository close.
- Phase 7: done for supervision and the client; the windows are not yet connected (phase 8). Swift side: `CoreServicing` is the app-facing protocol (plain Swift models; generated gRPC types stay inside `GRPCCoreService`), `CoreProcessSupervisor` is an actor with `start`, `recover`, `stop`, `service()` and a `states()` stream (`stopped`, `starting`, `running`, `lost`, `failed`). It launches the bundled helper with `serve --socket … --exit-on-stdin-eof`, waits for a `HealthCheck` with protocol version 1, and reports loss when the child exits. Concurrent `start()` calls share one launch. `HealthCheck` now also returns `process_id` (additive field 5) so a supervisor accepts only the Core it launched; a second instance gets exit status 3, is reported as `alreadyRunning`, and its socket is left alone. After our own Core exits, its stale socket is removed before the restart. `DesktopAppDelegate` starts the supervisor at launch and calls `terminateImmediately()` on termination; start failures are not yet shown in the UI. Verification: 19 new tests (fake-based state machine plus real helper over real gRPC: ten repositories on one Core process, repeated starts, event stream, SIGKILL then recover with a new pid, second supervisor refused, Core stops when its parent side closes stdin), 60 of 60 app tests pass. By hand with the built, unsigned app: one Core process, a second app instance did not start another, and killing the app with SIGKILL ended the Core. Not verified: the clean Cmd+Q path with the real app, a sandboxed signed build, a Core crash while a window shows data, reconnect of event subscriptions (phase 8). Added `grpc-swift-nio-transport` 2.11.0 (SPM). A hung test run showed that closing a gRPC connection with an open event stream blocks; the close now cancels after one second.
- Phase 8: done for open, close, refresh, events and the recovery offer; execution UI and file-grant bridging are not done. `CoreHub` (main actor) sits between `DesktopCoordinator` and the Core. Each workspace has its own observable `RepositorySession` (branch, workflows, last refresh, phase), so one repository's change redraws only its windows. The first window of a workspace opens the repository in the Core (idempotent), further windows share it, and the last close releases it; relinking to a new path closes the old repository and opens the new one; a window moved to another workspace releases the first. Refresh in the toolbar rescans through the Core next to the existing Swift file reload. Core events update only the matching session: `REPOSITORY_REFRESHED` reloads that workflow list, an outside `REPOSITORY_CLOSED` reopens it, `CORE_ERROR` is kept. If the event stream falls behind (`RESOURCE_EXHAUSTED`) the hub reopens everything and resubscribes. When the Core is lost or fails to start, every workspace window shows a banner with a Restart Core button; recovery restarts the single process and reopens all attached repositories. There is no automatic restart. The Swift file reader and editor paths are unchanged. Verification: 16 new tests (hub with a fake provider and service, plus coordinator integration), 76 of 76 app tests pass. With the real unsigned app and its saved session: the restored window opened its repository in the Core (open count 1, three workflows listed through `grpcurl`), killing the Core left the app running without spawning another, and quitting the app left no Core process. Not verified: the banner and Restart Core button on screen, closing a window with Cmd+W in the real app, and everything under a signed sandbox.
- Sandbox folder access for the Core: checked on 2026-10-17, see the next section. The earlier concern is partly confirmed (a denied folder looked empty) and partly not (the helper can use the app's grant).

## Sandbox Folder Access For The Core (2026-10-17)

Question: does the Core, a helper signed with `app-sandbox` + `inherit`, read a repository the user chose, when only the app holds the grant?

Method: an ad-hoc signed, sandboxed test app (the same entitlements as `Runnir.entitlements`) launched the real `runnir-core` helper (signed with `macos-helper.entitlements`) and kept it running. A separate unsandboxed process issued a read-only sandbox extension for this repository (`com.apple.app-sandbox.read`, the class a user-selected folder grant carries), and the app consumed it with `sandbox_extension_consume`. `OpenRepository` and `ListWorkflows` were then called on the helper's socket from outside. The harness lives outside the repository.

| Case | App can read | Core result |
| --- | --- | --- |
| No grant | no | Before the fix: `OpenRepository` succeeded with no branch and no workflows. After: `PERMISSION_DENIED` |
| Grant consumed before the helper starts | yes | branch and 3 workflows found |
| Grant consumed after the helper is already running | yes | branch and 3 workflows found |

Findings:
- The helper uses the app's grant, including one acquired after it started, so no extra file-descriptor or bookmark channel is needed for the basic case.
- The real risk was silent failure: stat is allowed but listing is not, so a denied folder looked like an empty repository. The scanner now probes the folder first and the Core returns `PERMISSION_DENIED` (`ErrAccessDenied`), which the app shows as "The Core cannot read this folder. Use Locate / Grant Access to renew access." A refresh that loses access keeps the last data and reports the error.
- Not verified: a grant obtained through `NSOpenPanel` and `startAccessingSecurityScopedResource` in a sandboxed Runnir build (the test used the same extension class but a raw API); a Developer ID signed and notarized build; behavior after `stopAccessingSecurityScopedResource` while the Core still has the repository open. A security-scoped bookmark made by the unsandboxed development build did not resolve in the test app, which has a different identity, so this was inconclusive; bookmarks saved by unsandboxed builds probably need re-granting after the move to a sandboxed build.

Proposed bridge, in order of preference:
1. Keep the current design and make it an invariant: the app holds the security-scoped access for as long as the Core has the repository open. Window grants already live as long as their windows, and the Core releases a repository with the last window. Add a manual release check with a signed sandboxed build before shipping (open a chosen folder, confirm the Core lists workflows, close the window, confirm the Core no longer can).
2. If a signed build shows the access is not shared, the fallback for direct distribution is a Core outside the App Sandbox (Developer ID, hardened runtime) with the Core enforcing granted roots itself, as ADR 0002 already requires. The app would pass only roots the user chose.
3. Reading through the app (Swift sends file contents to the Core) works under any sandbox, but moves workflow reading back into Swift and defeats the Core's purpose; use it only if option 2 is not acceptable.
Issuing extension tokens to the helper with private sandbox APIs is not recommended: it is unsupported and likely a distribution problem.
- Phase 9: done. `scripts/measure-resources.sh` measures the idle physical footprint (`footprint`, the figure Activity Monitor shows as Memory) and CPU of the app and its Core with 1, 3 and 10 repositories. For each count it builds fixture repositories (six workflow files each), launches the Debug app on an empty isolated session, has it open one window per repository through a Debug-only import hook (`--ui-testing` with `RUNNIR_UI_TEST_IMPORT_PATHS`; bookmarks must be created by the app itself, a bookmark made by another process did not restore), waits until the Core reports every repository open, settles 30 s, then samples. It refuses to run while another Core exists, needs `footprint` and `grpcurl`, and cleans up after itself. Result on 2026-10-17 (this Mac, macOS 27.0.1, arm64, Debug build, app on the Dashboard section, 30 s settle, 30 s CPU interval):

  | Repos | App MB | Core MB | Total MB | App CPU % | Core CPU % | Core processes |
  | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
  | 1 | 33.0 | 6.9 | 39.9 | 0.0 | 0.0 | 1 |
  | 3 | 44.0 | 7.8 | 51.8 | 0.0 | 0.0 | 1 |
  | 10 | 85.0 | 9.2 | 94.2 | 0.0 | 0.0 | 1 |

  Against the internal 300 MB target at 10 repositories the measured total is 94 MB. The Core grows by about 0.3 MB per repository; the app grows by about 6 MB per window and is the larger share. Read these numbers with care: one machine, a Debug build (a Release build should be measured before quoting figures), small fixture repositories, windows left on the Dashboard with no file opened, CPU resolution of about 0.03 percentage points (so "0.0" means below that), and no sandbox. `HealthCheck.resident_memory_bytes` is still the Go runtime's total, not the process footprint. There was no measurement of executions, event streams under load or large repositories.
