# Core gRPC API v1

Status: implemented in the Core and used by the desktop app, 2026-10-17. Decision and history: [ADR 0004](../decisions/0004-single-core-process-grpc.md) and the [implementation plan](core-process-plan.md). Source of truth for messages: `contracts/grpc/runnir/core/v1/runnir_core.proto`. The earlier [JSON-RPC stdio contract](ipc.md) remains for the version handshake.

## Process And Transport

- One Core per app instance. The app launches the bundled `runnir-core serve --socket PATH --data-dir SUPPORT --exit-on-stdin-eof` with Foundation `Process`. `--data-dir` is the app's support folder (`~/Library/Application Support/Runnir`, or the UI-test state folder), where each workspace keeps its database in `repositories/<workspaceId>/` ([ADR 0007](../decisions/0007-workspace-sqlite.md)); without it nothing is written to disk. Closing a window never stops it; quitting does.
- gRPC over a Unix domain socket, mode 0600, at `<per-user temporary directory>/runnir-core-<tag>.sock` where the tag is derived from the app bundle's path so that two copies of the app (a Debug build and an installed release) each run their own Core. The Core's standard error goes to `~/Library/Logs/Runnir/core.log`; the previous launch's log is kept as `core.previous.log`. No TCP listener. Paths over 103 bytes are refused.
- An advisory `flock` on `PATH.lock` allows one Core per socket. A second instance exits with status 3 and does not touch the running Core's socket. A stale socket is removed only while holding the lock. Other exit statuses: 0 clean stop, 1 failure, 2 usage.
- The Core stops on SIGINT or SIGTERM, or when stdin closes (the parent died). Stopping cancels running executions, ends event streams (`UNAVAILABLE`) and removes the socket.
- The app (`CoreProcessSupervisor`) waits for a `HealthCheck` that reports protocol version 1 and the pid of the child it launched; a Core answering with another pid is not accepted. While it runs, the supervisor asks for `HealthCheck` every 15 seconds; two unanswered checks in a row (3 seconds each) count as a hung Core, which is stopped so it releases the instance lock. When the child exits or hangs, the state becomes `lost` and each workspace window offers "Restart Core" and "Show Log". There is no automatic restart. If the event stream ends while the Core still runs, the app subscribes again (with backoff up to 30 seconds) and reloads every open repository, because events may have been missed. The Core syncs each open workspace's GitHub activity itself, once per workspace however many windows show it: every 20 seconds while a run is queued or in progress, every 5 minutes otherwise, with backoff when GitHub is unreachable or rate-limiting, and not at all after a sign-in problem until the token changes or the app asks. The app shows the saved activity at once and reads it again on `ACTIVITY_CHANGED`.

| `SaveJobLog(job_id)` | The whole log of one job written to `runnir-logs/<owner>-<name>-job-<id>.log` in the user's temporary folder (written to a temporary file first, then renamed over an earlier one; the system cleans the folder up), with its `path`; the app opens it in an editor. At most 256 MiB is read (`stopped_early` when the log is larger). `availability`: `AVAILABLE` with a path, `EXPIRED` when GitHub no longer has the log. The download gives up after 5 minutes with `UNAVAILABLE`; the app waits 330 seconds. The same redirect rules as `GetJobLog` | `INVALID_ARGUMENT` (missing job id), `INTERNAL` (the file could not be written) |
| `PrepareRunAction(run_id, action, job_id)` → `ConfirmRunAction(action_id)` | Cancel a run, re-run all its jobs, re-run its failed and cancelled jobs, re-run one job and the jobs that need it (`RUN_ACTION_RERUN_JOB`: `job_id` is required; Prepare reads the job and returns it as `job`, refuses a job of another run or one that has not finished, and a run that is still going, with a `problems` entry; Confirm posts once to the job's `rerun` endpoint), or approve the deployments a `waiting` run needs (`RUN_ACTION_APPROVE_DEPLOYMENTS`: Prepare reads the run's pending deployments and names in `environments` those the user may approve; Confirm approves them once, and needs the GitHub App's "Deployments: Read and write"), in two calls like a dispatch. Prepare reads the run and refuses an action that does not fit its current state (cancel a finished run, re-run an active one, re-run failed jobs of a successful one) with a readable `problems` entry; it returns the run as read. Confirm sends the request once and never retries; GitHub then cancels or starts the new attempt asynchronously, so `accepted_at` means accepted, not done. A run that changed state in between, or a change GitHub refuses for another reason (for example a run older than a month), comes back as GitHub's `rejection` text (HTTP 409, 422, or 403 on a change; a 403 on a read, or GitHub's "not accessible by integration" for a missing installation or permission, stays `NOT_VISIBLE`). This also applies to `ConfirmWorkflowDispatch` | Prepare: `INVALID_ARGUMENT` (also a re-run of a job without `job_id`), `RESOURCE_EXHAUSTED` (20 pending); Confirm: `FAILED_PRECONDITION` (expired or used), `NOT_FOUND` (repository closed since) |
| `SubscribeEvents` | First message `CORE_READY` with the baseline sequence, then repository and execution events, optionally filtered by `repository_ids`; events without a repository always pass | ends with `RESOURCE_EXHAUSTED` when the subscriber falls behind (queue of 256), `UNAVAILABLE` at shutdown |

Local runs are executions: they emit the same `WORKFLOW_*` events, closing the repository cancels them, and stopping the Core interrupts them and removes their containers (the Core waits up to 20 seconds for that).

Events: `REPOSITORY_OPENED`, `REPOSITORY_REFRESHED`, `REPOSITORY_CLOSED`, `ACTIVITY_CHANGED` (a workspace's saved activity or its freshness changed: at the start and end of each sync pass), `WORKFLOW_STARTED`, `WORKFLOW_STATUS_CHANGED` (queued, cancelled), `WORKFLOW_COMPLETED`, `WORKFLOW_FAILED`, `CORE_ERROR`. `sequence` is monotonic per Core process and matches delivery order; a gap or `RESOURCE_EXHAUSTED` means: resubscribe and reload state. Nothing keeps event history.

The scanner reads the branch from `.git/HEAD` (also linked worktrees; detached HEAD gives an empty branch), never follows symlinks, and treats an unreadable folder as an error rather than an empty repository. `Repository.origin_host` is the `origin` remote's host (lowercased, without port) in the repository's git config (the main repository's config for a linked worktree); `github_repository` is its `owner/name` and `github_server_id` its server when the host is github.com or an Enterprise server the Core holds. The raw remote URL is never sent because it can embed credentials.

## Compatibility

Package `runnir.core.v1`; generated Go and Swift code is committed (`scripts/generate-contracts.sh`). Clients check `protocol_version` before other calls.

Until the first release tag the contract changes in place: the app and the Core ship in one bundle and nothing outside it calls the Core yet, so fields and calls are changed or removed without keeping old forms (see AGENTS.md). CI runs `buf breaking` (FILE rules) only once the repository has a version tag. From the first tag on, additive fields and calls keep the package and a breaking change needs `v2`.

## Security Model Today

The socket is reachable only by the same user. On top of that, the app starts the Core with `--client-secret-stdin` and writes a fresh 32-byte random secret as the first stdin line; it never appears in argv or the environment. Every call except `HealthCheck` must carry `authorization: Bearer <secret>`, otherwise the Core answers `UNAUTHENTICATED`. `HealthCheck` stays open so the supervisor can see a Core answer; it returns only versions, counts and the process id. Without the flag, as with a manual `runnir serve`, the Core accepts any local client.

The app hands the signed-in user's GitHub token to the Core with `SetGitHubCredential` after sign-in or restore, again after every Core restart, and clears it on sign-out or when GitHub rejects it (`ClearGitHubCredential`). Each Enterprise server's token is handed over the same way, and a removed server is cleared by its id. A local run of a working tree on an Enterprise server gives act `--github-instance` with the server's web host, so `uses:` actions come from it; act never gets a token. The Core keeps it in memory only; no call returns it, and `HealthCheck` reports only `github_credential_set`.

This makes the app the only full client. Other clients such as an MCP adapter still need their own restricted identity, per-client leases and an approval authority; see [MCP readiness](mcp.md#readiness-against-the-grpc-core-api).

Runnir and the Core run without the App Sandbox ([ADR 0005](../decisions/0005-developer-id-without-app-sandbox.md)). The Core's own rules (reads only inside the chosen folder, no symlinks or `..` out of it, bounded reads, single-use confirmations for changes) are the main protection, and a folder macOS refuses (TCC) is reported as `PERMISSION_DENIED`, never as an empty repository.
