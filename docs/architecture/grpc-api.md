# Core gRPC API v1

Status: implemented in the Core and used by the desktop app, 2026-10-17. Decision and history: [ADR 0004](../decisions/0004-single-core-process-grpc.md) and the [implementation plan](core-process-plan.md). Source of truth for messages: `contracts/grpc/runnir/core/v1/runnir_core.proto`. The earlier [JSON-RPC stdio contract](ipc.md) remains for the version handshake.

## Process And Transport

- One Core per app instance. The app launches the bundled `runnir-core serve --socket PATH --exit-on-stdin-eof` with Foundation `Process`. Closing a window never stops it; quitting does.
- gRPC over a Unix domain socket, mode 0600, at `<per-user temporary directory>/runnir-core-<tag>.sock` where the tag is derived from the app bundle's path so that two copies of the app (a Debug build and an installed release) each run their own Core. The Core's standard error goes to `~/Library/Logs/Runnir/core.log`; the previous launch's log is kept as `core.previous.log`. No TCP listener. Paths over 103 bytes are refused.
- An advisory `flock` on `PATH.lock` allows one Core per socket. A second instance exits with status 3 and does not touch the running Core's socket. A stale socket is removed only while holding the lock. Other exit statuses: 0 clean stop, 1 failure, 2 usage.
- The Core stops on SIGINT or SIGTERM, or when stdin closes (the parent died). Stopping cancels running executions, ends event streams (`UNAVAILABLE`) and removes the socket.
- The app (`CoreProcessSupervisor`) waits for a `HealthCheck` that reports protocol version 1 and the pid of the child it launched; a Core answering with another pid is not accepted. While it runs, the supervisor asks for `HealthCheck` every 15 seconds; two unanswered checks in a row (3 seconds each) count as a hung Core, which is stopped so it releases the instance lock. When the child exits or hangs, the state becomes `lost` and each workspace window offers "Restart Core" and "Show Log". There is no automatic restart. If the event stream ends while the Core still runs, the app subscribes again (with backoff up to 30 seconds) and reloads every open repository, because events may have been missed. GitHub runs are re-read every 20 seconds while one is queued or running and every 5 minutes otherwise.

## Calls

Every repository call carries `repository_id`: `repo_` plus a hash of the first resolved path, stable across close and reopen.

One check runs at a time | `NOT_FOUND` (repository or workflow), `PERMISSION_DENIED` |
| `SaveWorkflowFile(workflow_id, content, base_sha256, overwrite)` | Replaces an existing workflow file the user edited: a regular file directly in a `.github/workflows` that is not a symlink, at most 1 MiB of UTF-8, written through `os.Root` so no path leaves the repository. The new content goes to a temporary file in the same folder and replaces the file in one rename; the file keeps its permissions. The file is only written while its SHA-256 still equals `base_sha256` (the version the editor loaded), checked before writing and again right before the rename; otherwise `conflict` is set, `sha256` names the version on disk and nothing changes. `overwrite` skips that check, for an explicit "Save Anyway". A file without the owner's write permission is not written. After a save the repository is scanned again, so `ListWorkflows` and events show the new file | `NOT_FOUND` (repository or workflow), `INVALID_ARGUMENT` (too large, not UTF-8), `FAILED_PRECONDITION` (read-only, or no longer a regular workflow file) |
| `StartWorkflow` | Starts or queues an execution of a copy of the scanned workflow without a reviewed plan; the act runner refuses it ("workflow execution engine is not available in this build"). | `GetToolReadiness(refresh)` | The act bundled with the app (next to the Core), an installed act (shell `PATH`, then Homebrew, `/usr/local/bin`, OrbStack, Docker Desktop and other usual locations; at least 0.2.60, newer than the bundled version marked `untested`), the Docker CLI, and the engine of the current Docker context: name (OrbStack, Docker Desktop, Colima, Rancher Desktop, Podman, Docker Engine), context, endpoint without user information, whether it is on this computer, versions, architecture, CPUs and memory. States: `FOUND`, `MISSING`, `STOPPED` (configured but not answering), `UNSUPPORTED` (too old, or a remote engine), `FAILED`. Read-only: runs `act --version`, `docker --version`, `docker context inspect`, `docker version` and `docker info` with the user's home and a short `PATH`, nothing else from the environment. The last result is reused unless `refresh` | |
| `PrepareLocalRun(workflow_id, job_id?, event?, use_installed_act)` → `ConfirmLocalRun(confirmation_id)` | A local run takes two calls. Prepare checks the tools again, reads the workflow file (bounded, no symlinks) and parses it with actionlint's parser. The plan has the event (one of the workflow's triggers; default push, pull_request, workflow_dispatch), the chosen job and the jobs it needs (or every job), and for each job whether it can run: `SUPPORTED` (an `ubuntu-*` runner act stands in for), `UNSUPPORTED` (macOS, Windows, self-hosted, runner groups), `UNKNOWN` (runs-on expressions, reusable workflows). It also lists the images (runner, `container:`, services, `docker://` steps) and whether the engine has them, the secrets the workflow reads (local runs get none), notes, and limits: 4 CPUs, 8 GB memory and 30 minutes, lowered to the engine's capacity. | `CancelExecution(execution_id)` | Removes a queued execution, or interrupts act (SIGINT to its process group, SIGKILL after 8 seconds) and removes the run's labelled containers. Cancelling a finished local run succeeds | `NOT_FOUND` |
| `SetGitHubCredential`, `ClearGitHubCredential` | Hold or forget the user's GitHub token in memory | `INVALID_ARGUMENT` (not a token shape) |

Only open repositories can be queried. GitHub-side outcomes come back in `status.access`: `OK`, `NO_REMOTE`, `SIGNED_OUT`, `TOKEN_REJECTED` (the Core forgets the token), `NOT_VISIBLE` (app not installed or no access), `RATE_LIMITED` (with `retry_after`), `UNAVAILABLE` | `NOT_FOUND` (unknown repository), `INVALID_ARGUMENT` (limit over 100, missing run id) |
| `ListGitHubRefs` | Default branch, up to 300 branches and 100 tags of the GitHub repository | as above |
| `DescribeWorkflowDispatch(workflow_path, ref)` | Whether the workflow can be started by hand at that ref and its `workflow_dispatch` inputs (type, required, default, options), read from the workflow file on GitHub at that ref, because that is the version GitHub runs. `NOT_VISIBLE` also covers a file missing at that ref; invalid YAML is reported in `parse_error` | `INVALID_ARGUMENT` |
| `PrepareWorkflowDispatch(workflow_id, ref, inputs)` → `ConfirmWorkflowDispatch(dispatch_id)` | Starting a workflow takes two calls. Prepare resolves the workflow's path from its id, reads it at the ref, and validates the inputs as GitHub will: unknown names, required values, choice options, booleans, numbers, at most 25. Problems come back as readable `problems`; otherwise it returns a single-use `dispatch_id` that expires after 2 minutes (at most 20 pending). Confirm sends exactly the prepared request once, never retries, and returns `dispatched_at`, `run_id` when GitHub reports it, or GitHub's `rejection` text | Confirm: `FAILED_PRECONDITION` (expired or used), `NOT_FOUND` (repository closed since) |
| `GetJobLog(job_id)` | The end of one job's log: at most 2 MiB of text and 50,000 lines, cut at a line start, with `truncated` set when earlier lines were dropped (line `number`s still count from the start of the full log). Each line comes without its timestamp, terminal colors and workflow command marker, tagged with a `kind` (`ERROR`, `WARNING`, `NOTICE`, `COMMAND`, `GROUP`, `END_GROUP`, `DEBUG`, `PLAIN`; a line starting with `error:` also counts as an error) and the `step_number` that was running when it was written, matched by the step start times GitHub reports. Lines longer than 8 KiB are cut. `availability`: `AVAILABLE`; `NOT_READY` (the job has not finished, or finished less than two minutes ago and GitHub is still storing the log; ask again); `EXPIRED` (retention passed or the log was deleted). A job that never ran (skipped, or cancelled before any step started) has no log and is `AVAILABLE` with no lines. `stopped_early` means the log is larger than the 256 MiB the Core reads, so the lines end before the log does. The download gives up after 2 minutes with `UNAVAILABLE`, before the app's 150-second deadline. GitHub redirects the download to short-lived storage; the token is sent only to the API, never to that storage, and only https targets are followed | `INVALID_ARGUMENT` (missing job id) |
| `PrepareRunAction(run_id, action)` → `ConfirmRunAction(action_id)` | Cancel a run, re-run all its jobs, or re-run its failed and cancelled jobs, in two calls like a dispatch. Prepare reads the run and refuses an action that does not fit its current state (cancel a finished run, re-run an active one, re-run failed jobs of a successful one) with a readable `problems` entry; it returns the run as read. Confirm sends the request once and never retries; GitHub then cancels or starts the new attempt asynchronously, so `accepted_at` means accepted, not done. A run that changed state in between, or a change GitHub refuses for another reason (for example a run older than a month), comes back as GitHub's `rejection` text (HTTP 409, 422, or 403 on a change; a 403 on a read, or GitHub's "not accessible by integration" for a missing installation or permission, stays `NOT_VISIBLE`). This also applies to `ConfirmWorkflowDispatch` | Prepare: `INVALID_ARGUMENT`, `RESOURCE_EXHAUSTED` (20 pending); Confirm: `FAILED_PRECONDITION` (expired or used), `NOT_FOUND` (repository closed since) |
| `SubscribeEvents` | First message `CORE_READY` with the baseline sequence, then repository and execution events, optionally filtered by `repository_ids`; events without a repository always pass | ends with `RESOURCE_EXHAUSTED` when the subscriber falls behind (queue of 256), `UNAVAILABLE` at shutdown |

Local runs are executions: they emit the same `WORKFLOW_*` events, closing the repository cancels them, and stopping the Core interrupts them and removes their containers (the Core waits up to 20 seconds for that).

Events: `REPOSITORY_OPENED`, `REPOSITORY_REFRESHED`, `REPOSITORY_CLOSED`, `WORKFLOW_STARTED`, `WORKFLOW_STATUS_CHANGED` (queued, cancelled), `WORKFLOW_COMPLETED`, `WORKFLOW_FAILED`, `CORE_ERROR`. `sequence` is monotonic per Core process and matches delivery order; a gap or `RESOURCE_EXHAUSTED` means: resubscribe and reload state. Nothing keeps event history.

The scanner reads the branch from `.git/HEAD` (also linked worktrees; detached HEAD gives an empty branch), never follows symlinks, and treats an unreadable folder as an error rather than an empty repository. `Repository.github_repository` is `owner/name` when the `origin` remote in the repository's git config (the main repository's config for a linked worktree) points at github.com; the raw remote URL is never sent because it can embed credentials.

## Compatibility

Package `runnir.core.v1`; `buf breaking` (FILE rules) guards it, and generated Go and Swift code is committed (`scripts/generate-contracts.sh`). Additive fields and calls keep the package; a breaking change needs `v2`. Clients check `protocol_version` before other calls.

## Security Model Today

The socket is reachable only by the same user. On top of that, the app starts the Core with `--client-secret-stdin` and writes a fresh 32-byte random secret as the first stdin line; it never appears in argv or the environment. Every call except `HealthCheck` must carry `authorization: Bearer <secret>`, otherwise the Core answers `UNAUTHENTICATED`. `HealthCheck` stays open so the supervisor can see a Core answer; it returns only versions, counts and the process id. Without the flag, as with a manual `runnir serve`, the Core accepts any local client.

The app hands the signed-in user's GitHub token to the Core with `SetGitHubCredential` after sign-in or restore, again after every Core restart, and clears it on sign-out or when GitHub rejects it (`ClearGitHubCredential`). The Core keeps it in memory only; no call returns it, and `HealthCheck` reports only `github_credential_set`.

This makes the app the only full client. Other clients such as an MCP adapter still need their own restricted identity, per-client leases and an approval authority; see [MCP readiness](mcp.md#readiness-against-the-grpc-core-api).

Runnir and the Core run without the App Sandbox ([ADR 0005](../decisions/0005-developer-id-without-app-sandbox.md)). The Core's own rules (reads only inside the chosen folder, no symlinks or `..` out of it, bounded reads, single-use confirmations for changes) are the main protection, and a folder macOS refuses (TCC) is reported as `PERMISSION_DENIED`, never as an empty repository.
