# 0006 Bundled act for Local Runs

Status: accepted, 2026-10-20.

## Context

Local runs (FR-06) execute workflows with [act](https://github.com/nektos/act) on the user's Docker-compatible engine. Runnir drives act through its command line and its JSON log format (`--json`). Neither is a stable API: act is still 0.x, flags get deprecated, and log fields can change. Supporting every act a user may have installed would mean testing a version matrix. The engine is different: Runnir only uses long-stable Docker CLI commands, and act negotiates the Engine API version itself.

## Decision

- Runnir bundles one act version, the one local runs were verified with, and uses it by default. It is built from source during the app build from the module pinned in `third_party/act` (currently v0.2.97, since 2026-11-11; v0.2.89 before). `go.sum` checks every module it is built from, so nothing is downloaded as a prebuilt binary. Like the Core, it is a universal helper in `Contents/Helpers/act`, signed with the hardened runtime and no entitlements. act's MIT license and those of the modules it is built from ship in `Contents/Resources/Licenses/notices.json` (B49).
- Settings has an experimental switch, **Use installed act**, which is off by default. When it is on and an installed act is usable (0.2.78 or newer, the first with `--concurrent-jobs`, found in the shell `PATH` or the usual install locations), runs use that act instead. Versions newer than the bundled one are labelled as not verified. Without a usable installed act, runs use the bundled act, and the review says so.
- The container engine stays the user's own (OrbStack, Docker Desktop, Colima or another Docker-compatible engine), reached through the current Docker context. The engine needs Engine API 1.41 (Docker 20.10) or newer. An engine whose context points at another computer is refused. Runnir never installs a tool by itself, starts an engine or switches the context. For an installed act, Settings › Tools can open Terminal with `brew install act`, which runs only when the user presses Return there (added 2026-10-23); without Homebrew it opens act's installation instructions.
- Every run uses a fixed act command line. Nothing from the repository adds flags. Values are joined to their flags and the event comes after `--`. Only event names in the shape GitHub allows reach act (`push`): a workflow that lists `--bind` as an event cannot add a flag. The command line enforces the following:
  - since 2026-11-08 a run is a scenario ([B32](../superpowers/specs/2026-10-25-scenario-pipeline-design.md#local-scenario-runs-s10-s11)): act runs once per ticked workflow, one after another, with `--workflows` naming a copy of the file in the run's scratch folder that holds only the ticked jobs and the jobs they need (made from the file as reviewed; `--job` is not used), `--eventpath` naming the scenario's event payload there (refs, base and head, so `github.ref` and `github.event.*` are the scenario's), and the lane's event from the reviewed plan after `--`;
  - `--json` and `--rm`;
  - `--pull=false`, so an image is downloaded only when it is missing;
  - `--network bridge`, not the engine's host network, which on some engines reaches the Mac's own services;
  - `--no-cache-server`, because the cache server listens on a network address of the Mac;
  - `--use-new-action-cache` (since 2026-11-11): a remote action comes from a bare repository as the files of the commit its ref resolves to. act's default cache checks an action out in a folder that parallel jobs of a matrix reset while another job copies it, so a job could get the action without some of its files (seen as `Cannot find module …/dist/cache-save/index.js` in a cross-build matrix); it also never moved a tag such as `v7` once fetched. The flag exists since act 0.2.60, older than the oldest installed act Runnir accepts (0.2.78);
  - `--container-daemon-socket -`, so the engine's socket is never mounted;
  - an empty `--env-file` and `--input-file`, and `--secret-file` and `--var-file` naming `secrets.yaml` and `vars.yaml` in the scratch folder, links to pipes act inherits (fd 3 and 4) that carry the values the user set for the run (B28) as JSON, so a repository's `.env`, `.secrets`, `.vars` or `.input` is never read and no value is on disk, in argv or in act's environment; `GITHUB_TOKEN` is always among the secrets, empty unless the user set it, so act never asks the `gh` CLI for one;
  - job containers get a label with the run's id and CPU and memory limits;
  - `--concurrent-jobs` (since 2026-11-15): half the Mac's performance cores (every physical core of an Intel Mac), at most one job for each 8 GB of memory, at least one; 3 on a Mac with 8 performance cores and 24 GB, 1 on an 8 GB Mac, which runs jobs one by one. act's default, one job per logical CPU, ran the eight jobs of Runnir's Go Core workflow at once, each container allowed 4 CPUs and 8 GB, and filled the Mac's memory and swap;
  - every runner label act can stand in for is mapped to act's medium images.
- Jobs on a `macos-*` runner (since 2026-11-08, on a Mac only): act runs them on the Mac itself (`--platform=<label>=-self-hosted`, labels in the shape `macos-…` only), and that lane's act runs under `sandbox-exec` with a profile that closes the home folder but for the repository, writes outside the run's folders, the Keychain's and the pasteboard's services, unix sockets in the home folder and launchd's (the engine's, SSH agents) and what starts outside the sandbox (`lsopen`, `appleevent-send`, `job-creation`); act in the sandbox gets no container engine, so a workflow with jobs on this Mac and in containers runs as several acts in turn, and act's cache there is the workspace's own (since 2026-11-16); shims for `xcodebuild`, `swift` and `sudo` come first on the PATH, as the [design](../superpowers/specs/2026-10-25-scenario-pipeline-design.md#macos-jobs-on-this-mac) says. They are ticked only by hand and confirmed apart. For one run the user may take them out of the sandbox (for `xcodebuild test`, which cannot run in one) after a second, harsher warning; act then runs without `sandbox-exec`, still with the `sudo` shim.
- act runs in a private scratch directory, with its own home and configuration directories. This keeps the user's and the repository's `.actrc` from applying. act gets no Docker credentials and no environment from the Core. `ACT_DISABLE_VERSION_CHECK=1` stops act's request to its notice service, which would otherwise send act's version, OS and architecture on every start.
- act runs a step of a job on this Mac from a script in its cache folder and splits the script's path at spaces. When the app's Caches folder has one (Runnir Dev and Runnir Local, or a home folder with a space), a lane with jobs on this Mac gives act the run's own cache folder instead, and fetches its actions again (found 2026-11-11: every Mac job of Runnir Local failed at its first `run` step; the end-to-end test of a Mac job now uses a cache path with a space).
- Jobs that need GitHub do not run locally (since 2026-11-11). A job with a step that uses an action working only in a run on GitHub, because it needs GitHub's APIs about the pull request or the repository or the run's OIDC token, is not supported locally with a reason that starts with "Only on GitHub": `actions/dependency-review-action` (GitHub's dependency graph), `actions/attest-build-provenance`, `actions/attest-sbom` and `actions/attest` (an attestation signed with the run's OIDC token), `actions/deploy-pages` (GitHub Pages with that token) and `github/codeql-action/upload-sarif` (code scanning). A job that needs such a job cannot start without it and is marked the same way. These jobs are never ticked, and a run that names one (an agent through MCP, or Run Again of an older run) is refused with the reason, instead of failing in act. The list is in `internal/localrun/github_only.go`.
- Local runs go one at a time, and so do the workflows of a run. act names containers after the workflow and job, so two at once could replace each other's containers. The time limit applies to each workflow.

## Consequences

- The app grows by about 20 MB per architecture, and the app build compiles act (cached after the first build).
- Updating act is a deliberate change: bump `third_party/act`, run the local-run tests, including `go test -tags e2e ./internal/localrun/` against a real engine, and update `TestedActVersion` in the Core.
- act's dependencies (including Docker and go-git libraries) are redistributed in the bundled binary. Their license notices are collected by `tools/notices` and ship with the app (B49); one of them, `github.com/cyphar/filepath-securejoin`, is partly MPL-2.0, and its source archive is named in the notices.
- Known vulnerabilities in the bundled act are Runnir's to handle. `third_party/act` raises act's dependencies where a fixed version is compatible. For act 0.2.89 it raised go-git to 5.19.3, golang.org/x/crypto to 0.58.0 with the x/net, x/sys and related modules they need, and klauspost/compress to 1.20.2, which fixed 19 findings govulncheck reported for act 0.2.89 as released; act 0.2.97 asks for x/crypto 0.58.0 itself, and Runnir keeps go-git 5.19.3 and klauspost/compress 1.20.2 above the 5.19.2 and 1.18.7 it asks for. CI scans the bundled act every week and on changes and fails on any reachable finding. GO-2026-6253 in moby/go-archive (a crafted tar archive can be written outside its extraction directory), listed as a known finding while act 0.2.89 needed an older go-archive, is fixed: act 0.2.97 uses go-archive 0.3.0.
- act 0.2.97 brought fixes from a security audit of act (GHSA-9j7q-g3ch-2283, GHSA-jpm2-x6wf-fxjc, GHSA-5xfg): action and reusable workflow paths stay inside their repository or the workspace, `NODE_OPTIONS` cannot be set through `GITHUB_ENV`, step output loses terminal control sequences and nested secrets are masked. Because Runnir passes `--container-daemon-socket -`, act's `auto` container options policy refuses what a workflow's `container:` or `services:` asks that would weaken isolation (`--privileged`, added capabilities, devices, the host's PID or network namespace, host path volumes). Runnir never passes `--container-options-policy=allow`, so such a job fails locally with act's message. Runnir's own `--container-options` (label, CPUs, memory) are not affected.
- Known act limitations, open upstream on 2026-11-11, that a local run can show and GitHub does not:
  - A matrix whose `runs-on` is an expression (`runs-on: ${{ matrix.os }}`): act evaluates it in the job shared by every entry, so all entries get the runner of the first entry evaluated, and an entry is skipped or runs on the wrong runner ([act#5971](https://github.com/nektos/act/issues/5971); the fix in [act#6050](https://github.com/nektos/act/pull/6050) is not merged). Since 2026-11-15 Runnir marks such a job not supported locally, with that reason, and never runs it; a `runs-on` expression that does not read the matrix still runs.
  - Jobs share the `act-toolcache` volume. The first time parallel jobs set up the same tool version that is not cached yet (for example `actions/setup-go` after a Go raise), they install it into the same folder at once and some of them fail; the install that remains is complete, so the next run passes.
  - A repository with `extensions.worktreeConfig`, which `git worktree` turns on and which Claude Code, Codex and similar tools leave in many repositories: act's go-git v5 refuses to open it, so act logs `unable to get git revision` on every step and `github.sha` stays empty in a pull request run. go-git fixed it only in v6, which act does not use yet ([go-git#1943](https://github.com/go-git/go-git/issues/1943)).
- The app marks local runs as Beta (since 2026-11-11) while these limitations stay open: the Run locally review, the Local run tab and the run's header carry the badge, and its tooltip says to check a failure on GitHub before changing the workflow for it.
- A local run belongs to its workspace and to the app. Three actions stop a running local run and remove its containers:
  - quitting Runnir;
  - closing the workspace's last window, which closes the repository in the Core;
  - opening another workspace in that window.

  Runnir asks before each of them.
- act keeps one shared named volume, `act-toolcache`, for tools that actions download, and reuses it across runs. It is not removed after a run; deleting it in the container engine only costs later runs those downloads.
- If the Core is killed during a run instead of being stopped (a crash, or a forced restart after it stopped answering), act is not interrupted. It may keep running until it fails to write its output, and its containers may remain.
- Containers act creates for services, or for jobs that set their own `container:` image, do not get Runnir's label or limits, because act passes container options only to job containers without a `container:` section. act removes those containers itself when it ends or is interrupted. If act has to be killed after the grace period, Runnir says that containers may remain.

## Verified

- On OrbStack with the bundled act v0.2.89 and the raised dependencies (end-to-end tests under the `e2e` build tag):
  - a job ran and its output and state came through;
  - the engine's socket was absent in the job;
  - secrets and `GITHUB_TOKEN` were empty;
  - a repository `.env`, `.secrets` and `.actrc` did not apply;
  - uncommitted files were copied and `.gitignore`d files were not;
  - a job container carried the run's label, 2 CPUs, 512 MB and the bridge network;
  - cancelling stopped the run in under a second and left no containers.
- On OrbStack with act v0.2.97 on 2026-11-11:
  - the end-to-end tests above passed, with the macOS job in the sandbox;
  - act with Runnir's flags (`--use-new-action-cache` included) ran Runnir's own Go Core `cross-build` matrix in `catthehacker/ubuntu:act-latest`: six parallel jobs fetched `actions/setup-go@v7` into an empty action cache and all succeeded, where act 0.2.89 with its default cache lost files of the action in one of them.
- Runnir's own CI workflows ran in `catthehacker/ubuntu:act-latest` with remote actions fetched through the raised go-git (act 0.2.89, 2026-11-10 and 2026-11-11); the failures they showed are the limitations listed above and a Dependency Review job, which needs GitHub.
