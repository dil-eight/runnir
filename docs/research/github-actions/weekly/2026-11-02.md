## Emerging trends

Status values at different levels can disagree: workflow versus job, matrix aggregate versus leg, and a selected successful check versus PR merge readiness. A reliable client should retain the underlying run, attempt, suite, check, and head identities rather than collapse them to one green status.

Elapsed-time displays also need evidence boundaries. A cross-level timestamp discrepancy should produce an explicit inconsistency state, not a confident queue-delay, ETA, or cost claim. Retain original timestamps so diagnostics remain auditable.

Missing schedule opportunities require a separate presentation from stuck queues. An expected-versus-observed comparison can identify a suspected gap, but cannot prove a dropped event or determine the backend cause. Replacing the missing execution automatically could duplicate time-sensitive work.

Local-runner compatibility remains relevant beyond YAML parsing. Registry-reference normalization and credential lookup can affect whether the same image runs locally. Recommendations should preserve explicit credential boundaries and avoid copying credentials into workflow files.

## GitHub API and upstream changes

- The [Jobs API for a specific run attempt](https://docs.github.com/en/rest/actions/workflow-jobs#list-jobs-for-a-workflow-run-attempt) supports bounded, paginated inspection with Actions read permission. A read-only inspection of [run 40772040230, attempt 1](https://github.com/stats-forge/github-stats-forge/actions/runs/40772040230/attempts/1) confirmed a cancelled macOS leg with no steps and successful CI OK. It does not establish the exact runtime needs context or explain GitHub's internal aggregation rule.
- The [needs context reference](https://docs.github.com/en/actions/reference/workflows-and-actions/contexts#needs-context) lists success, failure, cancelled, and skipped. It does not by itself settle the reported matrix edge case. To show complete coverage, compare observed jobs with the expected matrix; a nonempty list is insufficient.
- [Schedule documentation](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule) explicitly permits delay and dropped jobs under high load, requires the workflow on the default branch, and documents public-repository inactivity disabling. These are checks to consider, not proof that they caused E0035. The inspected Runs API lists existing runs; no documented dropped-tick history was identified.
- [Workflow runs](https://docs.github.com/en/rest/actions/workflow-runs) and [check runs](https://docs.github.com/en/rest/checks/runs) expose distinct records. Reruns require authorization and can be rejected. Runnir cannot force-complete or reconcile an internal job record through these read APIs, and a green check alone should not be labeled permission to merge.
- [GitHub Agentic Workflows became generally available on 2026-10-28](https://github.blog/changelog/2026-10-28-github-agentic-workflows-generally-available/), including CI failure analysis. This is upstream product context, not firsthand demand, a measured Runnir benefit, or justification to add AI infrastructure to the desktop MVP.

No new verified regression is added for historically resolved P21. Advice in community replies about support entitlements, backend repair capabilities, and mutation workarounds is not treated as official API behavior.

## Relevant feature requests and top three opportunities

The reports ask for explanations of missing schedule runs, the suite governing a blocked merge, and safe recovery of unstarted jobs. These are inspection and recovery requests; they do not authorize automatic cancellation, new dispatches, policy changes, or publishing private diagnostics.

1. **Show conclusion integrity:** inspect matrix legs and duplicate check suites at the exact run attempt and PR head; separate aggregate success from merge readiness.
2. **Explain contradictory state and time:** flag workflow/job disagreement and impossible timestamp ordering, preserving raw evidence and reporting rejected recovery requests accurately.
3. **Make suspected schedule gaps visible:** compare default-branch schedule expectations with observed runs and show coverage limits; leave any replacement execution under explicit operator control.

Roadmap recommendation: strengthen inspector and run-by-change diagnostics before introducing new infrastructure. Treat P22 as a focused P1 correctness candidate and P13/P20/P23 as P2 inspection work. Local compatibility remains P1, while a durable external scheduler stays outside the desktop MVP. No application behavior or acceptance gate is changed by this research update.
